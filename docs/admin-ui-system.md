# ScoreNow 관리자 UI 시스템

## 1. 목적과 적용 범위

이 문서는 `score-now-admin-fe` 관리자 화면의 시각적 일관성, 공통 컴포넌트 사용 기준, 반응형 동작과 검증 기준을 정의한다.

- 적용 영역: `src/views` 아래의 모든 관리자 화면
- 공통 UI 영역: `src/components/admin`, `src/components/common`, `src/styles`
- 신규 화면은 처음부터 이 규칙을 적용한다.
- 기존 화면은 기능 수정이나 UI 개선 대상으로 포함될 때 이 규칙에 맞춰 점진적으로 전환한다.
- 공통 `Base*`, `Admin*` 컴포넌트를 변경할 때는 관리자 프로젝트 전체 사용처의 영향도를 확인한다.

현재 구현된 각 화면은 이 규칙의 적용 사례일 뿐 시각적 기준 원천이 아니다. 특정 화면의 페이지 전용 스타일을 새로운 화면에 그대로 복사하거나, 화면을 보고 새로운 공통 규칙을 임의로 추론하지 않는다.

이 문서의 적용 범위가 프로젝트 전체라는 이유만으로 요청받지 않은 기존 화면을 한꺼번에 수정하지 않는다. 작업 범위는 유지하되, 새로 만들거나 수정하는 UI가 프로젝트 공통 규칙에서 벗어나지 않도록 한다.

## 2. 기준 원천

관리자 UI 판단에는 다음 원천을 사용한다.

1. 시각·사용 규칙: 이 문서
2. 색상·간격·크기의 실제 값: `src/styles/admin-tokens.css`
3. 공통 구조와 동작: `src/components/admin`, `src/components/common`

문서, 토큰, 공통 컴포넌트가 서로 다르면 불일치로 간주한다. 페이지별 예외로 덮기 전에 어느 원천을 변경할지와 기존 화면에 미치는 영향을 확인한다.

### 현재 기준의 상태

현재 관리자 UI 시스템은 디자이너 협의 전 마련한 초기 기준안이다. 프로젝트 전반의 일관성을 유지하기 위한 출발점이며 변경 불가능한 최종 디자인이 아니다.

- 디자인 협의에 따라 색상, 간격, 글자 크기, 컴포넌트 형태와 상태 표현을 수정할 수 있다.
- 공통 규칙을 변경할 때는 이 문서, `admin-tokens.css`, 관련 공통 컴포넌트를 함께 갱신한다.
- 공통 변경 전에 전체 사용처와 예상되는 시각적 영향을 확인한다.
- 한 화면만 임시로 덮어써서 공통 기준과 다른 상태를 장기간 유지하지 않는다.
- 도메인별 예외가 필요하면 예외의 목적, 적용 범위와 공통화하지 않는 이유를 남긴다.

## 3. 시각적 방향

- 정보 밀도가 높은 관리자 화면에 맞춰 간결하고 정돈된 구성을 사용한다.
- 흰색과 옅은 회색 표면을 기본으로 하고, 구분은 얇은 테두리와 제한적인 배경 차이로 만든다.
- 파란색은 주요 실행과 포커스, 초록색은 생성·등록, 빨간색은 삭제·오류에 사용한다.
- 상태를 색상만으로 전달하지 않고 텍스트 레이블을 함께 표시한다.
- 그라데이션, 큰 그림자, 과도한 아이콘, 불필요하게 강한 색상은 사용하지 않는다.
- 페이지마다 새로운 모서리 크기나 입력 스타일을 만들지 않는다.

## 5. 공통 컴포넌트 책임

### 목록 화면

| 컴포넌트 | 책임 |
|---|---|
| `AdminListPage` | 페이지 제목, 전체 여백, 요약·헤더 액션 슬롯 |
| `AdminFilterCard` | 검색 필드와 필드 바로 뒤의 액션 배치 |
| `AdminTableCard` | 결과 요약, 툴바, 테이블 내부 가로 스크롤 |
| `AdminTablePagination` | 페이지 크기, 현재 페이지, 이전·다음 이동 |
| `AdminTableState` | 로딩, 오류, 빈 결과 행 |

### 기본 UI

| 컴포넌트 | 책임 |
|---|---|
| `BaseButton` | 버튼 크기, 색상 우선순위, 비활성·포커스 상태 |
| `BaseInput` | 일반 텍스트·날짜·시간 입력 |
| `BaseSelect` | 단일 선택 입력 |
| `BaseTextarea` | 여러 줄 텍스트 입력 |
| `BaseBadge` | 모든 배지가 공유하는 크기·간격·모서리 |
| `AdminSportBadge` | 종목 레이블과 종목별 색상 조합 |
| `AdminDataOriginBadge` | 데이터 원천 레이블과 색상 조합 |
| `BaseModal` | 오버레이, 헤더, 본문 스크롤, 하단 액션 |

`BaseButton`, `BaseInput`, `BaseSelect`, `BaseTextarea`, `BaseBadge`, `BaseModal`은 전역 등록되어 있다. 화면에서 명시적으로 import할지는 기존 파일의 작성 방식과 테스트 환경을 따른다.

## 6. 전역 내비게이션

관리 영역과 영역 내부 기능을 다음 두 단계로 구분한다.

1. `AppHeader`: 경기 관리, 사용자 관리처럼 최상위 업무 영역을 전환한다.
2. `AppSidebar`: 현재 업무 영역 안의 세부 기능을 전환한다.

- 최상위 메뉴를 각 사이드바에 중복해서 배치하지 않는다.
- 로그인 성공과 `/admin` 기본 진입은 경기 리스트(`/admin/match/list`)를 사용한다.
- 경기 관리 화면은 `/admin/match/*`, 사용자 관리 화면은 `/admin/user` 경로를 사용한다.
- 메뉴 활성 상태는 현재 URL 또는 route meta를 기준으로 결정한다.
- 표시 문구만으로 전역 메뉴 활성 상태를 판단하지 않는다.
- 현재 영역의 메뉴는 색상과 옅은 배경을 함께 사용하고 `aria-current="page"`를 제공한다.
- 상단 메뉴를 선택하면 해당 영역의 기본 화면으로 이동한다.
- 좁은 화면에서도 경기·사용자 관리 메뉴와 로그아웃은 숨기지 않는다. 공간이 부족하면 사용자명과 긴 로고 표현을 먼저 축약한다.

사용자 관리 내부 사이드바는 아직 화면 로컬 상태를 사용한다. 해당 영역을 별도 전환 작업에 포함하기 전까지 기존 동작을 유지하며, 전역 내비게이션을 추가하기 위해 사용자 관리 내부 구현을 함께 변경하지 않는다.

## 7. 목록 페이지 구조

목록 화면은 특별한 이유가 없다면 다음 순서로 구성한다.

1. 페이지 제목과 선택적인 헤더 액션
2. 선택적인 현황 요약
3. 조회 필터 카드
4. 결과 요약과 페이지네이션이 있는 테이블 카드
5. 생성·수정 등 페이지 모달
6. 처리 결과 토스트

```vue
<AdminListPage title="페이지 제목">
  <template #header-actions>
    <BaseButton variant="success">+ 등록</BaseButton>
  </template>

  <AdminFilterCard aria-label="검색 조건">
    <div class="field-group">
      <label for="keyword">검색어</label>
      <BaseInput id="keyword" v-model="searchForm.keyword" />
    </div>

    <template #actions>
      <BaseButton variant="secondary">초기화</BaseButton>
      <BaseButton variant="primary">검색</BaseButton>
    </template>
  </AdminFilterCard>

  <AdminTableCard scroll-label="목록" table-min-width="960px">
    <template #summary>
      <strong>검색 결과</strong>
      <span>총 {{ totalElements }}건</span>
    </template>

    <table>...</table>
  </AdminTableCard>
</AdminListPage>
```

페이지 루트에 고정 `min-width`를 지정해서 좁은 화면의 내용을 잘라내지 않는다.

## 8. 조회 필터

- 필드는 `field-group` 안에 레이블과 컨트롤을 세로로 배치한다.
- 필드 폭은 데이터 성격에 맞게 페이지에서 지정하되, 작은 화면에서는 폭을 `100%`로 전환한다.
- 목록의 검색 실행 버튼은 `검색`으로 표시한다. 진행 상태를 버튼에 표시할 때는 `검색 중`을 사용한다.
- 검색 액션 순서는 기본적으로 `초기화 → 검색`이다. 마지막 검색 필드 바로 뒤에 배치하며, 카드 오른쪽 끝으로 밀지 않는다.
- 등록처럼 검색 조건과 무관한 페이지 주요 액션의 기본 위치는 `AdminListPage`의 `header-actions`다. 경기 리스트와 상단고정/핫매치에서는 검색과 등록을 연이어 수행할 수 있도록 `AdminFilterCard`의 `actions`에 `검색 → + 경기 등록` 순서로 배치한다.
- 작은 화면에서는 액션 영역을 다음 줄에 배치할 수 있다. 검색과 등록을 같은 영역에 둘 때는 두 버튼의 순서를 유지한다.
- 날짜·시간·일반 검색에는 `BaseInput`, 선택에는 `BaseSelect`를 사용한다.
- 비슷하게 보인다는 이유만으로 서로 다른 의미의 필드를 하나의 컴포넌트로 합치지 않는다.

## 9. 버튼 우선순위

| variant | 용도 |
|---|---|
| `primary` | 조회, 저장, 확인처럼 현재 흐름의 주요 실행 |
| `secondary` | 초기화 등 주요 액션을 보조하는 일반 실행 |
| `success` | 생성, 등록, 추가 |
| `outline` | 취소, 닫기, 이전·다음, 낮은 우선순위 작업 |
| `danger` | 삭제와 파괴적 작업 |
| `warn` | 주의가 필요한 비파괴적 작업 |

- 동일한 액션 그룹에서 같은 의미의 버튼은 같은 variant와 크기를 사용한다.
- 모달 하단은 `취소 또는 닫기 → 저장 또는 확인` 순서로 오른쪽 정렬한다.
- 관리 컬럼의 버튼 사이에는 간격을 둔다. 하나의 분할 버튼처럼 붙여 보이게 하지 않는다.
- 색상만 바꾸기 위해 페이지에서 `BaseButton` 내부 스타일을 반복 재정의하지 않는다.

## 10. 입력 컨트롤

- 일반 폼 입력은 높이 `34px`, 모서리 `6px`, 옅은 회색 배경과 얇은 테두리를 공유한다.
- 포커스는 파란 테두리와 공통 포커스 링으로 표시한다.
- 비활성 상태는 흐린 텍스트와 표면색을 사용하며 `disabled` 속성을 유지한다.
- 여러 줄 입력은 `BaseTextarea`를 사용하고 기본 최소 높이는 `96px`로 한다.
- 기본 컨트롤이 지원하지 않는 속성이 필요하면 먼저 Base 컴포넌트의 `$attrs` 전달 여부와 전체 영향도를 확인한다.

다음 입력은 네이티브 요소나 도메인 전용 스타일을 유지할 수 있다.

- 체크박스와 라디오
- 파일 업로드
- 테이블 셀 안의 인라인 편집 컨트롤
- 자동완성처럼 키보드·포커스 동작이 결합된 입력
- 점수·통계처럼 폭과 정렬이 특수한 숫자 입력

예외 입력도 색상, 모서리, 포커스 표현은 토큰과 같은 맥락을 따른다.

## 11. 테이블

- 테이블 헤더 높이는 `39px`, 본문 행 기본 높이는 `64px`다.
- 헤더는 중앙 정렬, 옅은 배경, `10px` 글자를 사용한다.
- 본문은 `11px` 글자와 얇은 행 구분선을 사용한다.
- ID와 숫자는 자리 폭이 흔들리지 않도록 tabular number 사용을 검토한다.
- 긴 텍스트는 컬럼 목적에 따라 말줄임, 줄바꿈 또는 최소 폭 확대 중 하나를 명시적으로 선택한다.
- 날짜와 시간처럼 한 단위로 읽는 정보는 아이콘과 값 사이를 과도하게 벌리지 않는다.
- 행 hover는 공통의 매우 옅은 배경을 사용한다.
- 수정된 행을 강조할 때는 강한 경고색 대신 옅은 상태 배경을 사용한다.

열이 많은 테이블은 다음 규칙을 따른다.

- `AdminTableCard`의 `table-min-width`에 필요한 최소 테이블 폭을 명시한다.
- 가로 스크롤은 페이지 전체가 아니라 테이블 카드 내부에서만 발생시킨다.
- 좁은 화면에서 컬럼을 무조건 숨기지 않는다. 정보 우선순위상 숨겨도 되는 컬럼인지 먼저 판단한다.
- 스크롤 영역에는 내용이 드러나는 `scroll-label`을 제공한다.
- 빈 상태는 현재 보이는 스크롤 영역 중앙에 유지한다.
- `AdminTableCard`를 사용하지 않고 가로 스크롤 테이블을 직접 구성하면서 `AdminTableState`를 사용하는 경우, 상태가 현재 보이는 영역 중앙에 위치하도록 스크롤 컨테이너에 `container-type: inline-size`를 선언한다.

## 12. 배지와 상태 표현

모든 배지는 `BaseBadge`를 디자인 원천으로 사용한다.

- 최소 높이: `23px`
- 좌우 여백: `8px`
- 모서리: `999px`
- 글자: `10px`, 굵기 `700`
- 색상 variant: `blue`, `red`, `yellow`, `green`, `gray`

종목과 데이터 원천처럼 도메인 의미가 있는 배지는 전문 컴포넌트가 레이블과 variant를 결정한다. 페이지에서 같은 매핑을 다시 작성하지 않는다.

- `green`: 정상·예정 또는 축구 계열
- `blue`: 주요 정보 또는 야구·BETS 계열
- `yellow`: 주의·수동·농구 계열
- `red`: 오류·실패·강한 경고
- `gray`: 미지정·비활성·중립

색상 의미가 충돌할 수 있는 새로운 상태는 기존 variant에 억지로 끼워 넣지 말고 공통 규칙 변경 필요성을 먼저 검토한다.

## 13. 로딩·오류·빈 화면

테이블 상태는 `AdminTableState`를 사용한다.

- `loading`: 로딩 표시와 진행 중 문구
- `error`: 오류 문구와 다시 시도할 수 있는 안내
- `empty`: 결과 없음과 검색 조건 안내

오류를 빈 결과처럼 표시하지 않는다. 상태 행의 `colspan`은 실제 컬럼 수와 일치시킨다. 짧은 로딩에는 `compact` 사용을 검토한다.

처리 결과 알림은 전역 `admin-toast.css`의 `.toast` 구조를 사용한다. 토스트의 표시 시간과 타이머는 각 화면의 비동기 흐름에 속하므로 공통 레이아웃 컴포넌트에 넣지 않는다.

## 14. 모달과 내부 폼

모달 셸은 `BaseModal`을 사용한다.

| size | 기본 폭 | 용도 예시 |
|---|---:|---|
| `sm` | `460px` | 확인, 짧은 단일 폼 |
| `md` | `560px` | 일반 생성·수정 폼 |
| `lg` | `720px` | 필드가 많은 폼 |
| `xl` | `880px` | 검색·선택·표를 포함한 복합 모달 |

- 특별한 외부 제약이 없다면 `width` 직접 지정보다 `size`를 사용한다.
- 헤더와 하단 버튼은 고정하고 본문만 세로 스크롤한다.
- 저장 중에는 `close-disabled`와 액션 버튼 disabled 상태를 함께 적용한다.
- 본문 최상위 폼에는 `modal-form`을 사용한다.
- 2열 구성은 `modal-grid` 또는 기존 `form-grid`를 사용한다.
- 필드는 `modal-field`, 레이블은 `modal-label`, 도움말은 `modal-help`, 오류는 `modal-error`를 우선 사용한다.
- 작은 화면에서는 모달을 가용 폭에 맞추고 2열 폼을 1열로 전환한다.
- 모달 하단에는 취소·확정처럼 모달 전체에 영향을 주는 액션만 둔다.
- 공통 확인창은 `AdminConfirmModal`을 사용한다. 일반 저장·변경은 확인에, 삭제·해제·외부 동기화·미저장 입력 폐기는 취소 또는 계속 편집에 초기 포커스를 둔다. 경기 Phase 전환과 경기 시작일 변경에도 취소를 기본으로 둔다.
- Enter는 포커스된 버튼을 실행하고 Escape는 확인창을 닫는다. 확인창을 닫으면 화면에 남아 있는 호출 버튼으로 포커스를 돌린다. 요청 처리 중에는 같은 작업을 다시 실행하지 않는다.

### 경기 대상 관리 모달

- 경기 단건을 대상으로 하는 관리 모달은 헤더에 작업명만 표시하고 경기 ID를 중복 표시하지 않는다.
- 본문 상단에는 경기 관리 도메인의 `MatchContextSummary`를 사용하여 대상 팀, 경기 일시, 경기 ID와 종목을 표시한다.
- 화면에만 필요한 부가 상태는 `badges` 슬롯으로 추가하고, 공통 경기 정보 구조에 도메인별 상태 로직을 넣지 않는다.

## 15. 반응형 규칙

관리자 화면은 브라우저 전체 폭이 아니라 실제 콘텐츠 영역의 너비를 기준으로 반응한다. 공통 목록 레이아웃을 사용하는 상위 콘텐츠 영역에는 `admin-content` 컨테이너를 제공한다.

```css
.admin-content {
  container-name: admin-content;
  container-type: inline-size;
}
```

기존 레이아웃에 컨테이너가 없다면 해당 화면을 공통 목록 구조로 전환할 때 함께 적용한다. 페이지마다 서로 다른 반응형 기준을 새로 만들지 않는다.

- `960px` 이하: 페이지 좌우 여백을 줄이고 화면별 복합 배치를 단순화한다.
- `600px` 이하: 페이지 여백을 `20px 12px 32px`로 줄이고 필터 필드를 한 줄에 하나씩 배치한다.
- 작은 화면에서 테이블 툴바와 페이지네이션은 줄바꿈을 허용한다.
- 테이블 자체는 필요한 최소 폭을 유지하고 카드 내부에서 가로 스크롤한다.
- 반응형 처리를 위해 핵심 데이터나 주요 액션을 임의로 숨기지 않는다.

viewport 미디어 쿼리와 container query를 혼용해야 한다면 적용 대상이 페이지 전체인지 모달·오버레이인지 구분한다. 관리자 콘텐츠 배치는 container query를 우선한다.

## 16. 공통화 판단 기준

다음 조건을 모두 만족할 때 공통 컴포넌트 추출을 우선 검토한다.

- 구조와 상호작용이 같은 실제 사용처가 둘 이상 있다.
- 페이지별 차이를 props 또는 slot으로 자연스럽게 표현할 수 있다.
- 공통화 후에도 도메인 로직이 컴포넌트 안으로 섞이지 않는다.
- 변경 시 영향을 받는 화면을 명확히 찾을 수 있다.

다음 경우에는 로컬 구현을 유지한다.

- 한 화면에서만 사용하는 선택 방식이나 편집 도구
- 종목별 중계처럼 도메인 동작이 강한 UI
- 모양은 비슷하지만 의미와 상태 전이가 다른 UI
- 미래의 재사용 가능성만 있고 현재 사용처가 없는 추상화

예를 들어 분할 선택 UI는 반복 사용처가 확인되기 전까지 `BaseSegmentedControl`로 만들지 않는다. 페이지 로컬 구현도 토큰과 버튼 우선순위는 따른다.

## 17. 금지 사항

- 페이지 전체에 큰 고정 `min-width`를 적용해 좁은 화면을 잘라내는 방식
- 공통 컴포넌트와 동일한 스타일을 페이지 scoped CSS에 복사하는 방식
- API 또는 데이터 모델 차이를 UI 공통 컴포넌트 내부에서 흡수하는 방식
- 사용처 확인 없이 공통 컴포넌트의 기본 디자인을 변경하는 방식
- 로딩, 오류, 빈 상태를 하나의 문구로 처리하는 방식
- 관리 버튼을 간격 없이 붙여 분할 버튼처럼 보이게 만드는 방식
- 기준 문서에 없는 강한 색상이나 장식을 페이지별로 추가하는 방식

## 19. 중계 패널

축구·야구 중계는 같은 패널 외형과 기본 편집 구조를 사용한다. 종목별 경기 규칙, 입력 모델과 저장 로직은 각 도메인 패널이 담당한다.

### 외곽과 헤더

- 오른쪽 고정 패널이며 상단 위치는 `52px`, 하단은 `0`, z-index는 `180`이다.
- 데스크톱 폭은 `clamp(560px, 48vw, 760px)`, 최대 폭은 `calc(100vw - 220px)`이다.
- 왼쪽 위·아래 모서리에 `--admin-card-radius`를 적용한다. 오른쪽 모서리는 화면 경계에 붙인다.
- 배경·테두리는 공통 surface·border 토큰을 사용한다. 외곽 그림자는 `-8px 0 24px rgb(15 23 42 / 14%)`를 기준으로 한다.
- 헤더는 고정하고 본문만 스크롤한다. 내부 입력에 포커스할 때 패널 외곽까지 스크롤되지 않도록 한다.
- 헤더 여백은 `16px`, 리그명은 11px/600 및 muted 색상, 경기 제목은 17px/700 및 title 색상이다.
- 헤더 오른쪽에 `채팅 보기 → 새로고침 → 닫기`를 배치한다. 일반 액션은 outline/sm, 닫기는 28px 버튼과 접근 가능한 이름을 사용한다.
- 미구현 액션은 비활성 상태와 이유를 제공한다. 샘플 화면의 새로고침은 실제 서버 조회로 오해하지 않게 동작을 안내한다.
- viewport 960px 이하에서는 전체 폭을 사용한다. 헤더 제목은 줄바꿈할 수 있고 주요 액션을 숨기지 않는다.

### 본문과 섹션

- 본문 여백은 `14px 16px 18px`이다.
- 기본 편집은 `경기 예정 시각 → 경기 상태 → 종목별 경기 진행·점수·상세 편집` 순서로 배치한다. 야구의 상세 중계 ON/OFF는 이 순서에 앞서 본문 최상단에 스위치로 제공한다.
- 섹션은 각각 둥근 카드로 감싸지 않는다. 상하 여백 `14px`와 하단 divider로 구분하며 첫 섹션의 상단 여백은 제거한다.
- 제목과 설명을 같은 묶음으로 세로 배치하고 섹션 헤더 아래에 `12px` 간격을 둔다.
- 제목은 13px/700 및 title 색상, 아래 설명은 11px 및 subtle 색상이다. 제목의 하단 여백은 `4px`이다.
- 섹션 저장 버튼은 입력 아래 왼쪽에 둔다. 액션 행 상단 간격은 `12px`, 버튼 간격은 `8px`이며 좁은 화면에서 줄바꿈을 허용한다.
- 이 규칙은 중계 패널의 섹션 액션에 적용한다. 모달 하단 버튼의 오른쪽 정렬 규칙과 구분한다.
- 상태 입력이나 전광판처럼 관련 입력을 묶는 내부 편집 영역에는 제한적으로 배경·테두리를 사용할 수 있다.
- 축구 경기 스탯과 야구 H/E/B의 미입력 칸에는 `-`를 안내 표시로 사용한다. 저장된 `0`은 숫자로 표시한다.
- 중계 멘트 입력칸에서 Enter로 등록하고 Shift+Enter로 줄바꿈한다. 멘트 저장 버튼도 같은 등록 동작을 실행한다. 한글 조합 중에는 Enter가 조합 입력에 사용되며, 저장이 실패하면 작성한 멘트를 유지한다.

### 종목별 편집 UI와 색상

- 패널 외곽·타이포그래피·액션 정렬은 동일하게 유지하되 경기 시계, 이닝, 카운트, 베이스 등은 종목 전용 UI로 둔다.
- 야구 이닝은 `1회초, 1회말, 2회초, …, 20회말` 순서의 단일 선택으로 제공한다.
- 이닝 점수 열은 `팀 → R(총점) → 1~20이닝` 순서이며 팀과 R은 왼쪽에 고정한다. 1–20이닝을 접기 없이 제공한다. 원정팀을 위에, 홈팀을 아래에 배치하고 표 내부에서만 가로 스크롤한다.
- 팀별 H/E/B는 이닝별 점수 바로 아래에 배치하고 상세 중계 ON/OFF와 관계없이 조회·편집·저장할 수 있다.
- 현재 이닝은 채도가 낮고 주변과 구분되는 배경으로 표시한다. 현재 이닝 레이블 및 `aria-current` 등으로 색상에만 의존하지 않는다.
- B/S/O는 누적 점등 램프로 표현하며 볼은 초록, 스트라이크는 노랑, 아웃은 빨강을 사용한다. 현재 숫자와 레이블을 함께 제공한다.
- 베이스는 2루 위, 3루 왼쪽, 1루 오른쪽, 홈 아래에 배치한다. 진루는 빨강과 진루 텍스트로 표현한다.
- 빨간 베이스·아웃 램프는 경기 상태를 나타내는 도메인 예외다. 삭제·오류 등 전역 색상 의미를 변경하지 않는다.
- 램프·베이스는 키보드로 조작 가능해야 하며 접근 가능한 이름과 `aria-pressed` 같은 상태를 제공한다.
- 상세 중계 스위치는 B/S/O, 주자, 투수·타자 편집 영역의 표시를 제어한다. 상세 중계 전환 시 편집 중인 입력값을 유지한다.
- 변경된 이닝 저장 시 카운트 초기화와 상세 중계 전환 시 편집 영역 표시 및 입력값 유지 동작을 검증한다.

### 일관성 검증과 공통화

- 같은 기능군의 패널을 비교해 폭·모서리·헤더·제목·설명·구분선·버튼 정렬의 차이를 확인한다.
- 공통 규칙과 종목별 예외를 구분하고 의도적인 차이는 이유를 남긴다.
- 재사용 구조가 안정되면 외곽 셸과 섹션 레이아웃의 공통화를 검토하되, 종목별 API와 상태 전이를 공통 UI에 넣지 않는다.


### 중계 패널의 미저장 변경 보호

- 축구·야구 패널은 닫기, 패널 새로고침, 다른 경기 중계로 전환하기 전에 미저장 변경을 확인한다. 변경이 없으면 바로 실행한다.
- 확인창은 `AdminUnsavedChangesModal`과 `useUnsavedChangesGuard`를 공유한다. 변경 감지와 저장 기준값은 각 패널이 관리한다.
- 취소하면 현재 경기와 입력값을 유지한다. 저장 중에는 닫기·새로고침·경기 전환 및 중복 저장을 막는다.
- 한 섹션을 저장한 후 재조회해도 다른 섹션의 미저장 입력은 유지한다. 서버에서 함께 변경되는 관련 필드는 갱신한다.
- 자동으로 흐르는 경기 시계와 로딩 상태는 미저장 변경으로 판단하지 않는다. 작성 중인 중계 멘트는 보호한다.
- 확인창은 계속 편집에 초기 포커스를 두며 Escape로 취소한다. 브라우저 탭 닫기와 다른 메뉴 이동 보호는 이 규칙의 구현 범위에 포함하지 않는다.
